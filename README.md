# Mini Assistant — RAG-сервис на Python

## 1. Описание проекта

**Mini Assistant** — учебный backend-проект, предназначенный для изучения принципов работы больших языковых моделей (LLM) и архитектуры Retrieval-Augmented Generation (RAG).

Основная задача проекта — реализовать упрощённый, но целостный RAG pipeline: от загрузки и обработки документов до поиска релевантной информации и формирования ответа с помощью языковой модели.

Проект разрабатывался в первую очередь для практического знакомства с основными этапами RAG, а также с инструментами и технологиями, которые используются при создании современных Python backend-приложений. Основной акцент сделан на понимании взаимодействия компонентов и принципов работы системы, а не на создании сложной масштабируемой инфраструктуры.

## 2. Поставленная задача

Разработать учебный backend-сервис на Python, демонстрирующий полный RAG-пайплайн:

- принимать и сохранять документы;
- разбивать текст документов на чанки;
- создавать и хранить embeddings;
- находить релевантные фрагменты по вопросу пользователя;
- передавать найденный контекст в LLM;
- возвращать обычный и потоковый ответы с источниками.

Дополнительно требовалось настроить PostgreSQL, миграции Alembic, HTTP API, тестирование и базовые проверки качества кода.

## 4. Последовательность реализации

Разработка проекта выполнялась постепенно, в соответствии с этапами M0–M7 из `SPEC.md`. Такой порядок был выбран специально: сначала был создан минимальный работающий каркас, затем к нему последовательно добавлялись хранение данных, обработка документов, поиск, обращение к LLM и потоковая выдача ответа. После каждого крупного шага проверялись не только отдельные функции, но и связь между компонентами.

### Начальный каркас: M0

На первом этапе была определена структура проекта. Код разделён на несколько зон ответственности:

- `app/main.py` отвечает за FastAPI-приложение и HTTP-роуты;
- `app/domain/` содержит независимую бизнес-логику: chunking, embeddings и retrieval;
- `app/db/` содержит модели, подключение к базе и repository;
- `tests/unit/` и `tests/integration/` разделяют быстрые тесты отдельных функций, были даны изначально.

Сначала в `main.py` был создан объект FastAPI и маршрут `GET /health`. Это было важно как минимальная проверка: приложение должно запускаться до того, как в него добавляются база данных и LLM. Затем была добавлена конфигурация, чтобы настройки не были разбросаны по коду и могли отличаться для обычного запуска и тестов.

### Конфигурация и логирование: M1

Далее была реализована модель `Settings` на основе Pydantic Settings. В неё вынесены URL базы данных и LLM, API-ключ, таймаут, настройки embedding-модели, параметры chunking, `top_k` и уровень логирования. Значения можно передавать через `.env` или переменные окружения, что позволяет не записывать настройки в исходный код и скрыть уязвимые данные.

Отдельно была предусмотрена настройка `test_database_url`. Пустая строка преобразуется в `None`, потому что отсутствие тестовой базы должно быть отличимо от заданного URL. Это используется интеграционными тестами: если тестовая база не указана, они пропускаются, а unit-тесты продолжают запускаться.

Для логгирования создан `logging_setup.py`. Он настраивает стандартный Python logging, задаёт уровень и формат сообщений. При запуске приложения логгер подключается в `lifespan`, а затем используется для сообщений о запуске, обработке маршрутов и ошибках при обращении к LLM. Логирование добавлялось не вместо ошибок API, а вместе с ними: клиент получает понятный HTTP-статус, а в терминале сохраняется техническая причина проблемы.

### База данных и хранение документов: M2

После каркаса была добавлена постоянная база данных. Для проекта выбран PostgreSQL, потому что документы и их чанки должны сохраняться между перезапусками приложения. SQLAlchemy используется как ORM-слой, чтобы описать таблицы Python-моделями и не писать все запросы вручную.

Были созданы две основные модели. `Document` хранит название и дату создания. `Chunk` хранит текстовый фрагмент, позицию внутри документа, ссылку на документ и embedding. Между таблицами настроена связь через `document_id`, а каскадное удаление нужно, чтобы удаление документа не оставляло в базе его старые чанки.

Структура базы вынесена в Alembic-миграции. Это позволяет создать таблицы одинаково на разных компьютерах и не зависеть от ручного редактирования PostgreSQL через Adminer. Для работы приложения добавлены `make_engine` и фабрика сессий.

SQL-запросы были отделены от маршрутов в `repository.py`. В repository реализованы создание документа вместе со всеми чанками в одной транзакции, получение одного документа, список документов, список чанков и подсчёт чанков. Такое решение выбрано потому, что `main.py` должен заниматься HTTP-логикой, а не деталями SQL-запросов.

### Обработка текста и загрузка документов: M3

Следующим шагом была реализована загрузка документа через `POST /documents`. Обработка выполняется в определённом порядке: сначала Pydantic проверяет входные данные, затем текст разбивается на чанки, для каждого чанка создаётся embedding, после чего документ и чанки сохраняются в PostgreSQL.

В `chunk_text` используется разбиение по пустым строкам. Короткие абзацы объединяются, пока не достигнут заданного размера, а слишком длинные абзацы режутся на части. Также используется перекрытие `overlap` - это нужно, чтобы смысловая граница между чанками не обрывала контекст полностью.

На этом этапе сначала был добавлен `FakeEmbedder`. Он создаёт детерминированный вектор из хэша текста. Такой вариант удобен для тестов: результат предсказуем, модель не скачивается, а тесты не зависят от Torch.

Затем появился общий интерфейс `Embedder` и реализация `SentenceTransformerEmbedder`. Благодаря общему методу `embed()` остальной код не знает, используется fake-вариант или настоящая ML-модель. Выбор выполняется в `create_embedder()` по настройке `EMBED_BACKEND`.

Во время интеграции обнаружилось важное ограничение: документы и вопрос должны обрабатываться одним backend и одной моделью. Например, `FakeEmbedder` создаёт векторы размерности 16, а `paraphrase-multilingual-MiniLM-L12-v2` — размерности 384. Если смешать их в одной базе, косинусное сходство завершится ошибкой несовместимых размеров. Поэтому при переключении backend старые документы нужно удалить и загрузить заново.

В `lifespan` были собраны основные зависимости приложения: настройки, embedder, SQLAlchemy engine, фабрика сессий и LLM-клиент. После этого были добавлены маршруты просмотра списка документов и получения документа по идентификатору.

### Семантический поиск и обычный ответ: M4

После того как документы стали сохраняться, был реализован сам RAG-поиск. Для `POST /ask` сначала создаётся embedding вопроса. Затем из базы загружаются сохранённые чанки, и для каждого вычисляется косинусное сходство с embedding вопроса.

Результаты сортируются по убыванию оценки. При одинаковой оценке используется идентификатор чанка, чтобы порядок был детерминированным и одинаковым при повторных запусках. Из отсортированного списка выбирается `top_k` результатов. Для каждого выбранного чанка формируется `SourceOut`, чтобы API возвращал не только ответ LLM, но и источники, использованные для его построения.

Найденные фрагменты объединяются в контекст. В prompt передаются инструкции: отвечать на основе контекста, сам контекст и исходный вопрос. Такой порядок отделяет retrieval от generation: поиск определяет, какие данные дать модели, а LLM отвечает только после подготовки этого контекста.

Для общения с моделью создан отдельный `LLMClient` на HTTPX. Он отправляет запрос на OpenAI-совместимый адрес `{base_url}/chat/completions`, передаёт выбранную модель и список сообщений, а затем извлекает текст ответа. Ошибки сети, timeout и HTTP-ошибки LLM преобразуются в `503 Service Unavailable`, потому что проблема возникает во внешнем сервисе, а не в формате запроса пользователя.

На этапе тестирования реальный вызов LLM заменяется mock-ответом через `respx`. Это позволяет проверить формирование запроса и обработку ответа, не запуская модель во время каждого теста.

### Потоковый ответ: M5

После обычного `/ask` был добавлен `POST /ask/stream`. В этом режиме LLM не ждёт формирования полного ответа, а отдаёт его частями. Клиент читает SSE-строки OpenAI-совместимого формата, функция `extract_delta` извлекает текст из `choices[0].delta.content`, а FastAPI передаёт токены через `StreamingResponse`.

Наружу поток выдаётся в формате:

```text
data: {"token": "..."}
```

После окончания генерации отправляется специальное событие:

```text
data: [DONE]
```

Асинхронность на этом этапе используется именно там, где она нужна: HTTP-клиент LLM работает через `httpx.AsyncClient`, а поток читается через `async for`. При этом chunking, расчёт embeddings и текущий SQLAlchemy repository остаются синхронными, потому что это обычные локальные вычисления и синхронный database layer.

### Подключение реальных моделей и настройка окружения

После того как основные тесты заработали на fake embedding и mock LLM, проект был проверен с реальными компонентами. В Docker Compose был добавлен контейнер llama.cpp с моделью Qwen, а в настройках указан OpenAI-совместимый адрес LLM. Это позволило выполнять настоящий `/ask`, а не только проверять маршрут на тестовом HTTP-ответе.

Для embeddings была подключена реальная модель `paraphrase-multilingual-MiniLM-L12-v2` через `SentenceTransformerEmbedder`. Модель загружается лениво — не при импорте модуля, а при первом вызове `embed()`. Поэтому unit-тесты и запуск с `EMBED_BACKEND=fake` не требуют загрузки тяжёлой модели.

При проверке реального запуска отдельно диагностировались ошибки подключения к LLM, неправильный порт контейнера и несовпадение размерностей embedding. Это показало, почему адрес LLM и embedding backend должны настраиваться независимо: работа fake embeddings не заменяет доступность LLM.

### Кэширование embeddings и дополнительные возможности: M7

В качестве расширения M7 был добавлен простой кэш embeddings. Сначала был реализован `CachedEmbedder` как обёртка над базовым embedder, а не как отдельная логика в `main.py`. Это позволяет оставить маршруты неизменными: они по-прежнему вызывают `app.state.embedder.embed(...)`, не зная, выполняется ли расчёт заново или используется кэш.

Кэш хранит вектор каждого текста в памяти процесса. При повторном запросе для уже встречавшегося текста модель повторно не вызывается. Ключ включает backend, название модели и исходный текст. Это необходимо, потому что один и тот же текст может иметь разные векторы у разных моделей, а fake и реальная модель имеют разную размерность.

Кэш выбран в памяти, потому что это простой и понятный вариант для учебного проекта: он не требует новой таблицы и миграции. Его ограничение состоит в том, что данные исчезают после перезапуска приложения и не разделяются между несколькими процессами.

Кроме кэша был добавлен скрипт оценки, который отправляет набор вопросов к `/ask`, измеряет время ответа и его объём и сохраняет результаты. Таким образом, M7 использовался не только для добавления функций, но и для практической проверки поведения сервиса.

### Проверка результата

На протяжении разработки использовались unit-тесты для chunking, embeddings, retrieval и LLM-клиента, а также integration-тесты для API и repository. Интеграционные тесты подключаются к отдельной PostgreSQL-базе, используют fake embeddings и подменяют LLM, поэтому их результат не зависит от скачивания модели или доступности реального сервиса.

В результате получился сквозной pipeline: документ принимается API, разбивается на чанки, получает embeddings и сохраняется в PostgreSQL; вопрос преобразуется в embedding, по базе выбираются релевантные чанки, их содержимое передаётся LLM, а клиент получает ответ и источники — обычным или потоковым способом.

## 5. API

В приложении реализованы следующие HTTP-маршруты:

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/health` | Проверка работоспособности сервиса |
| POST | `/documents` | Загрузка и индексация документа |
| GET | `/documents` | Получение списка документов |
| GET | `/documents/{id}` | Получение информации о документе |
| POST | `/ask` | Получение ответа с использованием RAG |
| POST | `/ask/stream` | Получение потокового ответа через SSE |

Для проверки API и просмотра автоматически сгенерированной документации FastAPI используется `/docs`.

## 7. Запуск проекта

Команды выполняются из корня проекта на новом компьютере.

### 1. Клонировать проект и создать окружение

```powershell
git clone <URL_репозитория>
cd mini_assistant_student
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

### 2. Подготовить настройки

```powershell
Copy-Item .env.example .env
```

Проверь в `.env` значения `DATABASE_URL`, `LLM_BASE_URL`, `LLM_MODEL` и параметры embeddings.

### 3. Запустить PostgreSQL и LLM

```powershell
docker compose up -d
```

### 4. Применить миграции

```powershell
alembic upgrade head
```

### 5. Запустить приложение

```powershell
python -m app.main
```

После запуска документация API доступна по адресу `http://localhost:8000/docs`.

## 8. Тестирование и проверка качества

Для проверки корректности выполнения работы есть модульные и интеграционные тесты.

Модульные тесты проверяют отдельные компоненты приложения:
- конфигурацию;
- разбиение текста на фрагменты;
- создание embeddings;
- вычисление сходства и выбор Top-K;
- обработку ответов и потоковых данных LLM.

Для запуска тестов:

```bash
pytest -q
```

Проверка стиля кода:

```bash
ruff check .
```

Проверка типизации:

```bash
mypy app
```

## 9. Ограничения текущей реализации

В текущей версии используются следующие упрощения:

- Для хранения embeddings применяется JSON-представление в PostgreSQL, без отдельной vector database.
- Поиск реализован через вычисление косинусного сходства и ранжирование результатов.
- Используется базовая стратегия разбиения текста.
- Не реализованы гибридные и сложные стратегии retrieval.
- Не предусмотрена полноценная система оценки.
- Отсутствуют механизмы масштабирования.

## 10. Результаты работы

В результате разработки получен небольшой backend-сервис, демонстрирующий полный цикл работы RAG-приложения:

- загрузку и индексацию документов;
- разбиение текста на фрагменты;
- создание и хранение embeddings;
- семантический поиск релевантной информации;
- формирование контекста для языковой модели;
- получение обычных и потоковых ответов от LLM.

В процессе разработки удалось на практике познакомиться с основными инструментами Python backend-разработки: FastAPI, SQLAlchemy, PostgreSQL, Alembic, HTTPX, Docker и Pytest.

Главный результат проекта — практическое понимание того, как отдельные этапы RAG взаимодействуют друг с другом и как организовать минимальную backend-инфраструктуру для приложения, использующего языковую модель.
